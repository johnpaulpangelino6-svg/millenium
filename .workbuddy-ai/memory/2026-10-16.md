# 2026-10-16 — Sign-in: explicit School / Corporate client category

## Request
"fix the sign in add if they are schools or corporate so that it will show in dashboard admin"

## The bug that was actually there
`POST /api/auth/register` **guessed** the client category from keywords in the
organization name:

```js
clientType: orgName.toLowerCase().includes('inc') || …('corp') || …('bank')
  ? 'corporate' : 'school'
```

Anything without those three tokens became a **school**. Proved it live by
registering "Globe Telecom" → stored `client_type = 'school'`. The registrant was
never asked, and the admin dashboard's school/corporate split was therefore
wrong for most corporate clients.

## Change
1. **`public/index.html`** — the single full-width "School / Organization" field
   became a 2-column row holding that field **plus** a new
   `#regClientType` select (🏫 School / University · 🏢 Corporate / Business).
   It carries `display:none` inline so it starts hidden.
2. **`public/js/app.js`**
   - `updateRegLocationLabel(role)` now also toggles the Client Category group,
     flips its `required`, and adds `.auth-field-group--span-2` to the org group
     when the selector is hidden — otherwise the org field sat stranded in the
     left half of a 2-up grid. Also sets the org placeholder per role.
   - Called from `switchAuthTab('register')` and once on `DOMContentLoaded`, so
     the form can never show a stale role/field combination.
   - `handleRegister()` reads `#regClientType`, sends it as `clientType`, and
     blocks a customer submit that has no category or no organization name.
3. **`src/routes/api.ts`** — accepts `clientType`, validates it against
   `['school','corporate']`, and treats it as **authoritative**. The old keyword
   heuristic survives only as a fallback for older clients that omit the field
   (and was widened with telecom/group/ltd/plc/industries/solutions/systems).
   Also: when the organization is already on file, do **not** silently
   reclassify it from a self-registration — log and leave it, so a typo in a new
   sign-up cannot overwrite an established client. Audit-log line now names the
   client type.
4. **`public/js/app.js` — admin dashboard.** The strip bar and the "By Client
   Type" box were fed by `state.devices` (`clientType` on the *device*), so a
   client that had just registered was invisible until a board was assigned to
   them. They now count **registered organizations** from `state.customers`:
   - strip → `🏫 School Clients: N` / `🏢 Corporate Clients: N`
   - client-type box → "Registered Clients by Type" + a `Manage →` link to
     `dataManager`/`customers`, and a "Latest sign-up: <org> <tag>" line.
   - The `active` chip is now the larger group instead of always Schools.
5. **`public/css/style.css`** — `.auth-field-group--span-2`; `.client-type-label`
   became flex so the Manage link sits flush right; new `.client-type-newest` /
   `.client-type-tag` rules, with dark values `#a8b6cc` / `#7dd3fc` / `#c4b5fd`
   (all ≥9:1 on `#060b19`) and light siblings `var(--text-secondary)` /
   `#0369a1` / `#6d28d9`. Deliberately **no `opacity`** on the sub-text: 0.72
   opacity over `#0d1733` computed to 4.27:1, under the 4.5:1 small-text bar.

`public/index.html` asset version `20261004j` → `20261004k`; `npm run build` run.

   and `top: 50px` + `height: calc(100vh - 50px)` (the `orientation: landscape`

   Explicit `top: 0; height: 100vh` in the new `@media (max-width: 900px)`
   block wins on source order.
3. **Three header-era mobile rules silently hid sidebar content** — they were
   written to save width in a 390px header, not in a 250px drawer:
   `.auth-user-info { display: none }` (killed the user's name),
   `.system-status-pill { display: none }` (≤700px, killed "Online"), and
   `.smartboard-badge { display: none }`. All three are re-shown scoped to
   `.app-sidebar`.

Also zeroed `@media (max-width: 1279px) .app-container { padding: 16px }` — that
padding existed for the header band and left the sidebar off the viewport edge.

### TRAPS — read before touching the sidebar or the brand mark
- **Never hardcode a surface colour on `.app-sidebar`.** `#070d20` was the whole
  bug in (G). If a sidebar surface does not follow the theme, grep for a literal
  hex on the rule rather than assuming the token is wrong — measurement showed
  the theme *was* switching while the sidebar stayed put.
- **The float animation was declared ~5,000 lines away from the element it
  affected.** When any sidebar element "moves on its own", grep
  `animation:\s*float` and `@keyframes float` — do not start at the element's own
  rule. Also check for a hover `scale()`.
- **An interrupted turn leaves the asset version unbumped**, so `?v=` still
  points at cached CSS and the user sees the pre-fix render. After any
  `public/**` edit, confirm the bump actually landed before reporting done.
- **`tests/rental-privacy.test.cjs` seeds nothing** and reads whatever is in the
  database. `customer list is non-empty` and `the database really does hold
  bookings owned by other accounts` (logged as `others=0`) FAIL whenever the
  `rentals` table is empty — which it is: `src/db/seed.ts` seeds no rentals
  (verified: `SELECT COUNT(*) FROM rentals` → 0). These are **fixture
  preconditions, not regressions**; they exist so the privacy assertions cannot
  pass vacuously. All the security assertions around them still pass.
- **The landing page forces dark** (`<html data-theme="dark">` + an inline
  script that only removes it when `localStorage['millennium-theme'] ===
  'light'`). To see the white landing logo you must set that key — a fresh visit
  shows the dark `--surface`.
- `theme-switch.test.cjs:258` already asserts "sidebar is light" in light mode,
  so this fix is covered by the existing suite as well as the probe.
