# 2026-10-16 — Sign-in: explicit School / Corporate client category

## Request
"fix the sign in add if they are schools or corporate so that it will show in dashboard admin"

## The bug that was actually there
`POST /api/auth/register` **guessed** the client category from keywords in the
organization name:

```js
clientType: orgName.toLowerCase().includes('inc') || …('corp') || …('bank')
  ? 'corporate' : 'school'
```

Anything without those three tokens became a **school**. Proved it live by
registering "Globe Telecom" → stored `client_type = 'school'`. The registrant was
never asked, and the admin dashboard's school/corporate split was therefore
wrong for most corporate clients.

## Change
1. **`public/index.html`** — the single full-width "School / Organization" field
   became a 2-column row holding that field **plus** a new
   `#regClientType` select (🏫 School / University · 🏢 Corporate / Business).
   It carries `display:none` inline so it starts hidden.
2. **`public/js/app.js`**
   - `updateRegLocationLabel(role)` now also toggles the Client Category group,
     flips its `required`, and adds `.auth-field-group--span-2` to the org group
     when the selector is hidden — otherwise the org field sat stranded in the
     left half of a 2-up grid. Also sets the org placeholder per role.
   - Called from `switchAuthTab('register')` and once on `DOMContentLoaded`, so
     the form can never show a stale role/field combination.
   - `handleRegister()` reads `#regClientType`, sends it as `clientType`, and
     blocks a customer submit that has no category or no organization name.
3. **`src/routes/api.ts`** — accepts `clientType`, validates it against
   `['school','corporate']`, and treats it as **authoritative**. The old keyword
   heuristic survives only as a fallback for older clients that omit the field
   (and was widened with telecom/group/ltd/plc/industries/solutions/systems).
   Also: when the organization is already on file, do **not** silently
   reclassify it from a self-registration — log and leave it, so a typo in a new
   sign-up cannot overwrite an established client. Audit-log line now names the
   client type.
4. **`public/js/app.js` — admin dashboard.** The strip bar and the "By Client
   Type" box were fed by `state.devices` (`clientType` on the *device*), so a
   client that had just registered was invisible until a board was assigned to
   them. They now count **registered organizations** from `state.customers`:
   - strip → `🏫 School Clients: N` / `🏢 Corporate Clients: N`
   - client-type box → "Registered Clients by Type" + a `Manage →` link to
     `dataManager`/`customers`, and a "Latest sign-up: <org> <tag>" line.
   - The `active` chip is now the larger group instead of always Schools.
5. **`public/css/style.css`** — `.auth-field-group--span-2`; `.client-type-label`
   became flex so the Manage link sits flush right; new `.client-type-newest` /
   `.client-type-tag` rules, with dark values `#a8b6cc` / `#7dd3fc` / `#c4b5fd`
   (all ≥9:1 on `#060b19`) and light siblings `var(--text-secondary)` /
   `#0369a1` / `#6d28d9`. Deliberately **no `opacity`** on the sub-text: 0.72
   opacity over `#0d1733` computed to 4.27:1, under the 4.5:1 small-text bar.

`public/index.html` asset version `20261004j` → `20261004k`; `npm run build` run.

   and `top: 50px` + `height: calc(100vh - 50px)` (the `orientation: landscape`

   Explicit `top: 0; height: 100vh` in the new `@media (max-width: 900px)`
   block wins on source order.
3. **Three header-era mobile rules silently hid sidebar content** — they were
   written to save width in a 390px header, not in a 250px drawer:
   `.auth-user-info { display: none }` (killed the user's name),
   `.system-status-pill { display: none }` (≤700px, killed "Online"), and
   `.smartboard-badge { display: none }`. All three are re-shown scoped to
   `.app-sidebar`.

Also zeroed `@media (max-width: 1279px) .app-container { padding: 16px }` — that
padding existed for the header band and left the sidebar off the viewport edge.

## THE REAL "Forgot Password?" BUG — it was a z-index stacking trap, not the API

- Symptom reported by the user: clicking **Forgot Password?** on the sign-in
  screen did nothing at all. The API was never the problem (see above, 14/14).
- **Cause:** `#authPortalOverlay` (`public/index.html:94`) is the full-screen
  sign-in screen and is `.auth-portal-overlay`, a `position: fixed; inset: 0`
  overlay at **z-index 9999** with an opaque background
  (`#030612` + radial gradients). Every dialog built by `handleForgotPassword()`
  uses `.modal-backdrop`, which is **z-index 1000** (style.css:2533). So the
  dialog opened, was fully interactive, and was painted **entirely behind the
  sign-in screen** — indistinguishable from a dead button. No JS error, no
  network call, nothing to see in the console.
- **Same trap hit `.toast-notification`** (was z-index 2000, style.css): the
  reset flow ends with `showToast('✅ Password changed…')` while the sign-in
  screen is still up, so that confirmation was also invisible.
- **Fix:** added `.modal-backdrop--above-auth { z-index: 10000; }` and gave the
  forgot overlay that class; raised `.toast-notification` to `z-index: 10001`.
  Both stay under the notification panel (100000).
  Verified safe: `.modal-backdrop` and `.modal-backdrop--above-auth` have EQUAL
  specificity (0,1,0), so source order decides — the new rule is later
  (style.css:2561 vs 2533), so 10000 wins. No other `.modal-backdrop` rule sets
  `z-index` (the ones at 5135/6817 are inside `@media print`, 6727 is a
  max-width:639px padding tweak).
- Both `#authPortalOverlay` and the dialog are **direct children of `<body>`**,
  so they share one stacking context — that is what makes the comparison valid.
  If the portal were ever nested inside a transformed/filtered parent, its
  z-index would be scoped to that parent and this fix would stop working.
- **Stacking order is now:** 999 modal-ish → 1000 `.modal-backdrop` →
  2000→10001 `.toast-notification` → 9998 `.auth-modal-backdrop` →
  9999 `.auth-portal-overlay` → 10000 `.modal-backdrop--above-auth` →
  100000 notification panel. Anything else opened from the sign-in screen will
  hit this same trap and needs the same treatment.
- **Diagnostic lesson:** "the button does nothing" with zero console output and
  zero network activity is a *stacking/pointer-events* symptom, not a logic
  symptom. Check `z-index` of the container the button lives in before
  suspecting the handler.
- Also bumped `?v=` in `index.html` to `20261016b` (both style.css and app.js
  changed). `.modal-backdrop--above-auth` is the ONLY thing that makes the reset
  dialog reachable, so if the CSS version is stale the bug appears to persist.
  **Confirmed fixed by the user's screenshot** — the dialog now renders on top.

## The reset dialog's primary button froze on "Sending code…" — fixed

- User sent a screenshot of the reset dialog: the alert correctly said "This
  server has no email delivery configured…", but the button was **stuck reading
  "Sending code…"**. Two separate things in one frame; only the second was a bug.
- **Root cause, `public/js/app.js` `busy()`:**
  ```js
  primary.textContent = on ? (label || 'Working…') : primary.textContent;
  ```
  The else-branch assigns the property **to itself** — a no-op. The label set on
  the way in was never cleared, so "Sending code…" stuck forever. It affected
  **all three steps**, not just step 1: "Verifying…" and "Saving…" would freeze
  the same way. The button was actually re-enabled (`primary.disabled = false`),
  so it looked clickable but never changed text — which reads as a hung dialog.
- **Fix:** added `restingLabel` + `setPrimaryLabel(text)`; `busy(false)` now
  restores `restingLabel`. All three render functions call `setPrimaryLabel`
  instead of assigning `primary.textContent` directly, so the idle label can
  never drift from the current step.
- **Cache-busting was a trap:** `public/index.html` pins `app.js?v=…` and
  `style.css?v=…`. Both files changed, so the version had to be bumped or the
  browser would serve the **cached old app.js** and the fix would appear not to
  work. Bumped `20261016d` → `20261016e`. Note the value is `20261016d`, not
  `20261016` — a `[0-9.]+` regex silently truncates the trailing letter.
- **Second change — dev-only setup hint.** `src/routes/api.ts` now adds
  `mailSetupHint` alongside `mailUnavailable`, **only when
  `NODE_ENV !== 'production'`**, and `app.js` renders it escaped via
  `escapeHtml` under the error. Rationale: the person running this locally is the
  person who can fix it, so a dead-end message wastes a round trip; but a public
  deploy must not advertise its own misconfiguration. Verified both paths by
  booting a second instance on `PORT=3099 NODE_ENV=production` — hint absent,
  dev instance present. New CSS class `.reset-pw-hint-inline` in `style.css`.

- **New `src/tools/brevo-connect.mjs` + `npm run mail:brevo`.** Brevo setup fails

  leave a broken `.env`. On failure it names the fix (e.g. "no verified sender →
  Senders, Domains & Dedicated IPs → Add a sender") rather than a status code.
- **Split into `src/tools/brevo-lib.mjs`** (pure logic: `validateKey`,

  `writeEnvValues`, `explainBrevoError`) with the CLI as a thin interactive shell.
  This was forced by a sandbox constraint, but it is better structure anyway.

### Environment gotcha: the sandbox HTTP proxy
`HTTP_PROXY`/`HTTPS_PROXY` are set to `http://127.0.0.1:53345` in this sandbox,
and Node's `fetch` in a **child process** cannot reach a mock server in the parent
process's localhost port — it times out, and the mock sees **no request**. Setting
`NO_PROXY=127.0.0.1,localhost` does **not** fix it. Note the asymmetry: a fetch to
a server in the *same* process works fine. **Do not build tests that spawn a child
process and expect it to talk to a local mock HTTP server** — inject `fetch`
instead. Real external hosts (api.brevo.com) do work from a child.
