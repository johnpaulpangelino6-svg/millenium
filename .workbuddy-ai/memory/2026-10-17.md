# 2026-10-17 — Millennium SmartBoard

## Mail: removed the restart footgun (live `.env` reload)

**Problem.** `dotenv` reads `.env` exactly once, at boot. The Brevo setup
wizard writes credentials while the dev server is already running, so the
server kept the old (empty) environment and still reported
"no mail transport configured". `tsx watch` does not watch `.env` either, so
nothing would ever pick the change up. This is the third time the user has hit
a "still not working" wall on this feature; a silent stale-environment trap was
a plausible contributor.

**Fix — `src/auth/mailer.ts`.**
- Added `refreshEnvFromDotenv()`, called at the top of `readConfig()`. It
  stats `.env`, and when the mtime changes, re-parses the file into
  `process.env`. Precedence still matches dotenv: a value that came from the
  real environment (shell export, Render dashboard var) is **never**
  overwritten by the file. Tracked via an `envOwned` map of values this module
  itself pushed, so the rule is self-priming and does not need a boot-time
  snapshot.
- `getTransporter()` now caches on a **config signature**
  (`provider|host|port|user|pass|from`) instead of a bare boolean, so a pool
  built from old credentials is discarded when `.env` changes. Without this the
  server would keep failing with credentials that no longer exist on disk.
- `DOTENV_PATH` is overridable via `MILLENIUM_DOTENV_PATH` — a test hook only,
  never set in normal use (same pattern as `BREVO_API_BASE`).

**Tests — `tests/env-hot-reload.test.cjs`, 6 assertions.** Runs against a
throwaway `.env` in a temp dir (the real one is never touched), imports the
real mailer in a child process, writes credentials mid-flight and asserts the
config flips from `none` → `brevo` with no restart, then asserts key rotation is
also seen. **Proved it catches the regression:** removing the
`refreshEnvFromDotenv()` call drops it to 2 passed / 4 failed.

**Copy fixes (the "restart the server" advice is now wrong everywhere):**
`src/routes/api.ts` dev hint, `src/tools/setup-mail.mjs` closing line,
`src/tools/brevo-connect.mjs` closing line.

**Verified:** `tsc --noEmit` rc=0; all four runnable suites green —
reset-dialog-button 14, brevo-wizard 38, env-hot-reload 6, otp-flow 22
(**80 total**); live endpoint still returns no code field and its dev hint no

## Environment quirk worth remembering

This sandbox routes outbound traffic through a proxy
(`HTTP_PROXY=http://127.0.0.1:53345`), and Node's `fetch` in a **child**
process cannot reach a localhost mock server even with `NO_PROXY` set. That
broke the first Brevo test design (15 of 25 failed for no real reason). The
workaround, applied twice now: split the logic into a pure module and inject
`fetch`, testing in-process rather than spawning a child against a mock.

## Brevo 401 — the two-secrets trap

The user's next attempt returned `HTTP 401 Brevo rejected the key`. The old
message only blamed an incomplete copy, which is not the most likely cause.

**The real trap: Brevo issues two secrets one letter apart.**

| Prefix | What it is | Works with `api.brevo.com`? |
|---|---|---|
| `xkeysib-…` | API key | ✅ yes — this is the one |
| `xsmtpsib-…` | SMTP key (relay only) | ❌ always 401 |

Both live under the same **SMTP & API** menu, on adjacent tabs, so picking the
wrong one is easy.

**Changes:**
- `src/tools/brevo-lib.mjs` — added `normalizeKey()` (strips surrounding
  quotes/backticks/whitespace and repairs a hard-wrapped paste; a key never
  contains whitespace so this is always safe), `keyKind()`
  (`api` / `smtp` / `unknown`), and `keyShapeWarning()`. `explainBrevoError()`
  now takes the key and branches: an `xsmtpsib-` key gets told it is an SMTP
  key, an API-shaped key gets told about both prefixes.
- `src/tools/brevo-connect.mjs` — normalises the paste and reports what it
  cleaned; **fails fast on an SMTP key without spending a request**; Step 1
  guidance now warns not to use the SMTP tab.

**Tests:** brevo-wizard went 38 → **67**. Suite total now **109**
(brevo-wizard 67, env-hot-reload 6, reset-dialog-button 14, otp-flow 22).
Verified against the real API: an `xsmtpsib-` key exits with the SMTP message
and no request; a quoted `xkeysib-` key reports the cleanup, reaches Brevo, and
gets a genuine 401; `.env` byte-identical afterwards in both cases.

**Still blocking:** a valid `xkeysib-` API key from the user.

## RESOLVED: the 401 was an IP allowlist, not a bad key

The user pasted a key: `xkeysib-` + 64 hex + 16 = 89 chars, perfect shape, but
still 401. **The key was valid all along.** Brevo's raw body revealed it:

> "We have detected you are using an unrecognised IP address 112.203.36.205.
> If you performed this action make sure to add the new IP address in this link:
> https://app.brevo.com/security/authorised_ips"

The account has **Authorised IPs** enabled. The user's IP is dynamic — it
changed on every request (`112.203.36.205`, `112.203.39.228`, `112.203.36.232`,
`180.190.85.115`, `180.190.84.99`), so allowlisting a single address would break
within minutes. **The correct fix is to switch the restriction off**, which also
matters for the Render deploy (different IP again).

**Lesson worth keeping:** Brevo returns 401 for *both* a bad key and an unlisted
IP. The generic "rejected the key / copied incompletely" message sent the user
down the wrong path entirely. Always read `body.message` before diagnosing a
401.

## The exact Brevo fix (from Brevo's own docs)

Article: **"Authorize and block IP addresses for API and SMTP security"**
`help.brevo.com/hc/en-us/articles/5740111683858`

**Why it happened:** for API keys Brevo runs a two-phase process. Phase 1 is a
"learning phase" — IPs that make API calls are auto-authorized, blocking
inactive. **Phase 2: if no new IPs are seen for 30 days, Brevo automatically
activates blocking** and emails the account owner. So this appears out of
nowhere on a key that was working fine before. Worth stating up front to anyone
who hits it.

**Deactivate (the fix):**
Settings > Security > Authorized IPs → under **Blocking unauthorized IP
addresses** → **API keys** row → **Deactivate for API** → **Deactivate
blocking**. Direct: https://app.brevo.com/security/authorised_ips

**Do NOT try to allowlist instead.** The user is behind carrier-grade NAT; the
observed IPs span two unrelated /16s (`112.203.x.x`, `180.190.x.x`) and changed
on every single request — even twice within one command. An allowlist cannot
hold. Same for the Render deploy, which has its own IPs.

**Also important:** the authorized-IP list is **shared between API and SMTP
keys**, and SMTP keys have *no* learning phase. So switching this app to Brevo's
SMTP relay would NOT dodge the block — it would need manual pre-authorization
and then break the same way. Don't propose SMTP as a workaround.

**Message improvements:** both `explainMailError()` (mailer.ts) and
`explainBrevoError()` (brevo-lib.mjs) now name the exact click path
("Deactivate for API") and explain the 30-day auto-activation.
**Tests: 123 passing** (brevo-wizard 81, env-hot-reload 6, reset-dialog-button
14, otp-flow 22).

## The dialog lied during the resend cooldown (fixed)

The user reported "showing this but still not sending to my gmail" with a
screenshot of the dialog reading **"A new code is on its way."** — i.e. the app
claimed success. It hadn't sent anything.

**Root cause.** The server enforces a 60s resend cooldown. Inside that window it
correctly sends nothing, but it still answers `success` — it has to, because a
different answer would reveal which addresses have accounts. The client had no
matching cooldown, so it rendered the success message for a send that was never
attempted. Verified live with two back-to-back requests:

| Request | Server did | Client said |
|---|---|---|
| 1st (fresh) | attempted → failed | error (correct) |
| 2nd (< 60s) | **nothing** | "A new code is on its way." ❌ |

This is the same silent-dead-end class as `mailUnavailable` / `mailFailed`, and
it is what made the user believe mail was working.

**Fix — `public/js/app.js`.**
- Added `RESEND_COOLDOWN_MS`, `lastCodeRequestAt`, `lastCodeEmail`, and a small
  pure `resendWaitMs(email, now)` so the rule is testable without a DOM.
- `requestCode()` refuses locally when a wait is pending, showing
  *"A code was already sent… wait N seconds"* (`.is-info`) instead of firing a
  request the server will ignore.
- `renderStep2()` disables the resend link and shows a live
  *"(available in Ns)"* countdown, re-enabling when it expires.
- `.reset-pw-link:disabled` added to `style.css`.
- Cache-busting bumped to `20261017b`.

**Test — `tests/reset-dialog-cooldown.test.cjs`, 21 assertions.** Extracts the
real `resendWaitMs` and runs it in a vm with controlled state (same technique as
reset-dialog-button). Covers blocking, exact-boundary expiry, per-address
isolation, first-request passthrough, and — section 6 — that the dialog actually
*wires the guard in*, since a correct pure function nobody calls is exactly how
the original bug survived. **Proved it catches the regression:** zeroing
`waitMs` drops it to 20/1 and exits 1.

**Tests: 144 passing** (reset-dialog-cooldown 21, reset-dialog-button 14,
brevo-wizard 81, env-hot-reload 6, otp-flow 22).

### Known limitation (not fixed, deliberately)
`mailFailed` is gated to non-production because `attempted` is true only for
addresses that exist, so exposing it in production would be an enumeration
oracle. In production a *failed* send is therefore still reported as success
(logged server-side). The clean fix if it matters: track consecutive send
failures and expose a server-wide `mailDegraded` flag once the transport is
clearly broken — that is identical for every address, so it leaks nothing.

### MAJOR BREAKTHROUGH: Brevo's SMTP relay is NOT IP-blocked

The user pasted an **SMTP key** (`xsmtpsib-…`) by mistake — they wanted the API
key. But testing it revealed the way through.

**Probe result** (`smtp-relay.brevo.com`, ports 587 and 465, login
`johnpaulpangelino6@gmail.com`, pass = the SMTP key):

```
535 5.7.8 Authentication failed
```

**That is not an IP block.** The TCP connection succeeded, Brevo completed the
SMTP handshake, and it rejected only the *username*. The HTTP API refuses with
"unrecognised IP address" instead. Brevo's docs confirm why: blocking is
activated **independently for API keys and SMTP keys**, and the SMTP side
requires *manual* activation — so the 30-day auto-activation only caught the API
side.

**Consequences worth remembering:**
- The user does NOT need to find Settings > Security > Authorized IPs at all.
  Configure Brevo SMTP instead and the whole allowlist problem disappears.
- Outbound ports 587/465 are open from this sandbox — no firewall issue.
- Two further facts: Brevo's SMTP **login is not the account email** on newer
  accounts (it is a generated `…@smtp-brevo.com` value shown on the same page as
  the key), and Brevo SMTP still requires a **verified sender address**.

**Config path:** the generic SMTP branch already in `mailer.ts` handles this —
`SMTP_HOST=smtp-relay.brevo.com`, `SMTP_PORT=587`, `SMTP_USER=<login>`,
`SMTP_PASS=<smtp key>`. **Caveat:** `readConfig()` checks `BREVO_API_KEY` FIRST,
so the (blocked) API key must be cleared or SMTP will never be reached.
