# 2026-10-01 — Backend / Database connection hardening

## Problem
User reported the database + backend connection was unreliable. Root cause found:
the **live server was running a stale `dist/` build**. `dist/server.js` and
`dist/db/database-supabase.js` were built at Oct 1 00:08, while `src/` gained
crash-guard code at 10:18–10:19 that never got compiled. Proven by probing the
running process: unknown `/api/*` routes returned the SPA HTML shell and
`/health` had no `databaseConnected` field — i.e. pre-fix code.

Because `npm start` and Render's `startCommand` both run `node dist/server.js`,
production would crash whenever Supabase's pooler dropped an idle connection
(no `pool.on('error')` listener => uncaught EventEmitter error).

## Fixes applied (code only — NO data changes, per .kiro/steering/database-protection.md)

### src/db/database-supabase.ts
- `connectionTimeoutMillis: 2000` -> `15000`. 2s is too tight for the Supabase
  pooler (`aws-0-ap-south-1.pooler.supabase.com`); it caused spurious connect
  timeouts on boot and under load. Combined with `process.exit(1)` on failure,
  a slow pooler handshake could stop the server from ever starting.
- Added `keepAlive: true` + `keepAliveInitialDelayMillis: 10000`.
- Added `withRetry()` helper with `TRANSIENT_DB_ERROR` regex
  (ECONNRESET|ETIMEDOUT|ECONNREFUSED|EPIPE|ENOTFOUND|EHOSTUNREACH|
  Connection terminated|terminating connection|timeout expired|Connection closed).
- `testConnection()` now retries 5x with linear backoff instead of throwing on
  the first transient blip.
- Added `ping()` — lightweight `SELECT 1` probe for the health endpoint.
- (already present from earlier work) `pool.on('error')` non-fatal handler.

### src/server.ts
- `/health` now actually checks the DB via `db.ping()`, returns
  `databaseConnected: boolean` and HTTP 503 when degraded (was a static string).
- Schema init wrapped in a 5-attempt retry loop for transient pooler errors.
- Added an `/api` JSON 404 handler **before** the SPA fallback. Previously any
  unknown `/api/*` path returned `index.html`, so the frontend reported a
  confusing JSON parse error instead of a clear 404.

## Verified after rebuild + restart
- `tsc --noEmit` exit 0; `npm run build` exit 0.
- All guards confirmed present in `dist/`.
- `/health` -> `databaseConnected: true`.
- Unknown `/api/*` -> JSON 404; non-API routes still serve `index.html`.
- 13/13 frontend endpoints HTTP 200 `success:true` (no HTML fallback).
- Login OK for admin / customer / technician; wrong password -> 401.
- Stress test: 100/100 requests HTTP 200 under 15-way concurrency, max ~2.2s,
  zero stderr output.

## Operational notes

  `C:\Users\LENOVO\.workbuddy-ai\binaries\node\versions\22.22.2-3\node.exe dist/server.js`.
- **Detached spawn (`child_process.spawn` with `detached:true`) is BLOCKED by the

# 2026-10-01 (later) — Customer rental/booking visibility fix

## Problem
Customer accounts saw the WRONG rentals in the booking/rental view.
`renderRentalsView()` filtered with a **case-sensitive, untrimmed** compare:
`r.customerName === state.currentUser.organization`.
Real data: user `orgen` has `organization = "qcu"` (lowercase) while rentals store
`customerName = "QCU"`. So `"QCU" === "qcu"` was false and the customer saw **0**
of their own bookings. Meanwhile the customer-portal widget lowercased both sides
and showed 3 — the two rental views disagreed.

Separately, `GET /api/rentals` returned **every** rental to **every** caller, so
the client-side filter was the only thing hiding other customers' data.

## Fixes

### src/routes/api.ts
- Added `resolveRequesterScope(userId)` — resolves the requester's role **from the
  database**, not from the client-supplied `userRole` (that param is no longer
  trusted for access control). For customers it resolves `customerId` (via
  `users.customerId`, falling back to matching `customers.organization_name`).
- Added `rentalInScope(rental, scope)` — case/whitespace-insensitive ownership
  test; matches the stable customer id first, then the organization name.
- Added `computeRentalStats(rentals)` — derives dashboard stats from a scoped list.
- `GET /api/rentals`: scopes to the requester's own bookings. **Fails closed** —
  a `userId` that cannot be resolved returns an empty list, never the full one.
  (No `userId` at all keeps the original admin behaviour.)
- `GET /api/rentals/stats/summary`: same scoping, so a customer never receives
  company-wide revenue/booking totals.

### public/js/app.js
- Added `rentalMatchesUser(rental, user)` and `getVisibleRentals()` — **one**
  ownership rule now shared by the Rentals page and the customer portal, so the
  two views can never disagree again.
- `renderRentalsView()` uses `getVisibleRentals()` (was the case-sensitive compare);
  the "Upcoming" stat card is now computed from the customer's own list instead of
  global stats (company-wide figures are admin-only).
- `renderCustomerBookings()` uses the same helper.
- `fetchAllData()` sends `userId`/`userRole`/`userOrganization` to `/api/rentals`
  and `/api/rentals/stats/summary` (mirrors the devices/tickets pattern).
- `openRentalModal()`: customers no longer see a `<select>` listing **every**
  organization; they get a read-only field plus a hidden `customerId`. If the
  account is not linked to any customer record, booking is blocked with a clear
  message instead of silently creating an unattributable rental.
- `openRentalDate()` / modal edit lookup now use `getVisibleRentals()`.

## Verified
- `tsc --noEmit` exit 0, `node --check public/js/app.js` OK, `npm run build` exit 0.
- Scoping matrix: no-params → 3; admin → 3; customer `orgen` → 3; customer
  `johnpaul` → 3; **unknown userId → 0**; **unknown id + `userRole=admin` → 0**
  (role spoofing no longer works). Scoped stats likewise return 0 for unknown ids.
- Old-vs-new frontend rule on live data: `orgen` OLD → **0** rentals, NEW → **3**.
- 14/14 endpoints HTTP 200; login still OK.

## Notes / limitations
- The app has **no API authentication** (login just returns the user object; there
  is no token). So this is UI-level scoping plus a fail-closed server default — not
  a hard security boundary. A caller who sends no `userId` still gets the full list.
  Real isolation would require adding auth tokens.
- The database currently holds only ONE customer org (QCU), so cross-tenant
  isolation could not be demonstrated with live data; the fail-closed tests stand in
  for it. Do NOT create test customers to prove it (see database-protection rule).
- `updateRental()` deliberately does not touch `customer_id`/`device_id`, so the
  disabled customer/device selects on the edit form are safe.

# 2026-10-01 (3rd follow-up) — "other user still sees other customer's booking"

User sent a screenshot of the Rentals page signed in as **John Paul Pangelino**,
org QCU, showing 3 rentals all labelled customer **QCU**, and believes this is a
leak.

## Finding: NOT a privacy bug — it is a single-org dataset
Investigation showed:
- The database contains exactly **ONE** customer organization: `CUST-1789631617438`
  = "QCU".
- All 3 rentals (RNT-2026-0001/0002/0003) therefore belong to QCU.
- `GET /api/rentals?userId=USR-1789631616961` (John Paul) returns 3 rows, all
  `customerName === "QCU"`, and the raw payload contains **no** other org name.
- Rental numbers are never reused either: DB total == 3 and the values match 1:1.

So the rows he sees ARE his own. The Rentals table always renders a "Customer"
column, which shows "QCU" on every row — that is what looked like someone else's
data. **Do NOT "fix" this by hiding the column; the data is correct.**

## Real bug found while investigating: stale cached session
The app caches the logged-in user in `localStorage` under `millennium_auth_user`
and, on page load, restored it verbatim:
```
state.currentUser = savedUser;
state.currentRole = savedUser.role;
```
It never re-checked the server. Consequence: if an account is deleted and
recreated (new id) — which happened to `johnpaulpangelino6@gmail.com`/
`johnpaulpangelino6` during earlier register experiments — the cached session
points at a **dead id** while the chip still shows the old name. The server then
fails the scope lookup closed and the user silently sees **0** bookings, with a UI
that claims they are someone else. Also `currentRole` could go stale.

### Fix: public/js/app.js
- Added `refreshAuthSession()` — on load, re-reads the account from
  `/api/auth/users` by id, verifies it still exists, rewrites the cached session,
  and returns `null` (forcing a clean login) if the account is gone. Falls back to
  the cached copy if the server is unreachable, so a network blip cannot lock a
  user out.
- `DOMContentLoaded` handler is now `async` and reconciles the session before
  trusting it.

## Note
Data only loads when a session exists (`fetchAllData()` is called only in the
`if (savedUser)` branch), so the default `state.currentRole = 'admin'` is never
used to fetch data — no cold-load leak. However the `/api/rentals` route still
returns the full list when `userId` is omitted, so **real auth tokens remain the
only genuine fix** for hard privacy. Repeated as the standing recommendation.

# 2026-10-01 (6th follow-up) — Fix the scanning features

## Root cause #1 — scanned device QR never matched a device
Device QR codes encode a **full URL**, e.g.
`https://millennium-smartboard.local/device/MIL-2026-00788?serial=SN-MIL86-2026-00788&customer=QCU`
but `validateWarrantyBySerial()` compared that whole string against
`device.id` / `device.serialNumber` → always failed. Every QR on a real sticker
was unscannable.

### Fix (public/js/app.js)
- `extractScannableToken(text)` — pulls the identifying token out of whatever was
  scanned: `?serial=|&sn=|&device=|&id=` query param first, then `/device/<id>`
  path, then last path segment of any URL, else the raw text.
- `findDeviceByScannedCode(rawCode, devices)` — exact `id`/`serialNumber` match
  first, then a tolerant both-ways `includes()` match so partially printed codes
  and case differences still resolve.
- `validateWarrantyBySerial()` now validates the **token**, not the raw payload.

## Root cause #2 — the app could not scan its own printed barcode
`generateWarrantyBarcode()` / `printWarrantyBarcode()` encoded
`device.serialNumber || device.id` while the QR encoded a URL — two different
payload conventions. The "Scan Warranty" button could not read the app's own
sticker.

### Fix
- Added `buildWarrantyBarcodePayload(device, opts)` — the single source of truth
  for the encoded value (bare serial, else bare id; empty string if neither).
- Both `generateWarrantyBarcode()` and `printWarrantyBarcode()` now use it, so
  the on-screen barcode and the printed sticker always encode the same value.
- Print path: guard for pop-up blocking, guard for missing serial, and escape the
  value before embedding it in the print window's inline `<script>`.
- `generateWarrantyBarcode()` now guards `typeof JsBarcode === 'undefined'`.

## Root cause #3 — scanner hardening (CDN + camera failures)
`html5-qrcode` and `JsBarcode` are CDN-hosted. If the CDN was blocked/offline the
old code threw `ReferenceError: Html5Qrcode is not defined` and left a blank modal.

### Fix
- Module state: `html5QrCode`, `scannerCameras`, `scannerHandlingResult` (debounce).
- `isScannerLibraryAvailable()` — checks both globals before any use.
- `describeCameraError(err)` — maps NotAllowed/NotFound/NotReadable/SecurityError
  to actionable messages instead of a generic failure.
- `startWarrantyScanner()` — library guard, `Html5Qrcode.getCameras()` to pick a
  rear/environment camera (multi-camera desktops), falls back to `facingMode`;
  on failure shows a specific message and returns to the instructions panel so the
  Upload/Manual paths stay reachable.
- `onScanSuccess()` — debounced via `scannerHandlingResult` so one scan runs one
  validation.
- `scanUploadedImage()` — rewrote the decode path. The old version declared
  `const html5QrCode = new Html5Qrcode(...)` which **shadowed** the module-level
  variable, then leaked the instance (never `clear()`ed on the success path).
- New `decodeBarcodeFromImage()` — tries `scanFileV2(File)` → `scanFileV2`
  downscaled → `scanFile(src)`, clears the instance in `finally`, always resolves.
- New `downscaleImageToDataUrl()` — phone photos are often 12MP+ and stall the
  WASM decoder; downscales to a 1200px max edge first.
- `handleBarcodeImageUpload()` — accepts by MIME **or** file extension (some
  Android/Windows pickers report an empty `file.type`); guards missing DOM nodes.
- `triggerBarcodeImageUpload()` — guards a missing input and clears `value` first
  so the same file can be re-picked.

## Verified
- `node --check public/js/app.js` OK; `npm run build` exit 0.
- **18/18 round-trip tests pass**, including the printed-sticker round trip
  (`buildWarrantyBarcodePayload` → `findDeviceByScannedCode` resolves for devices
  with a serial, with only an id, and rejects unknown/empty codes).

# 2026-10-01 (7th follow-up) — "No barcode detected in image" ROOT CAUSE

User reported the image-upload scan still failing with
`❌ No barcode detected in image.` (the 6th-follow-up fix was incomplete).

## Real root cause — WRONG API SIGNATURE
`html5-qrcode@2.3.8`'s `scanFileV2()` **rejects a data URL**. It requires a real
`File`/`Blob`:
```
scanFileV2(dataUrl) -> Error: imageFile argument is mandatory and should be
                       instance of File. Use 'event.target.files[0]'.
```
`scanFile(dataUrl)` fails the same way in this build. So two of my three decode
attempts (the downscaled-canvas and enhanced-canvas paths) could **never** succeed —
they both passed data URLs. The only working call shape is `scanFileV2(File)`.

Diagnosis method: drove the real app in headless Chrome (puppeteer-core, system
Chrome at `C:\Program Files\Google\Chrome\Application\chrome.exe`), generated a
CODE128 PNG with JsBarcode in-page, and called each decode variant directly. This
was worth doing — the bug was in the call shape, not the codec.

## Secondary findings from the same probe
- `#qrReaderContainer` measures **0×0** on the live page: its parent
  `#scannerCameraView` is `display:none` during upload. Verified that a 0×0 host
  still decoded fine in this version, but it is fragile/undefined behaviour —
  switched to a rendered but offscreen host anyway.
- Confirms the library itself is fine: `Html5Qrcode` + `JsBarcode` both load and
  `scanFileV2(File)` decodes correctly.

## Fixes (public/js/app.js)
- `decodeBarcodeFromImage()` — dropped the two data-URL attempts; now tries
  `scanFileV2(File)` first, then `scanFile`. Removed the dead branches.
- Added `createOffscreenScannerHost()` — a `position:fixed; left:-10000px;
  640×480` div appended to `<body>`, torn down in `finally`. Replaces reusing the
  hidden `#qrReaderContainer` for every attempt (which also collided across
  sequential attempts).
- Kept `downscaleImageToDataUrl()` / `enhanceImageForBarcode()` as image
  *pre-processing* helpers, but they must be converted to a `File` before
  `scanFileV2` — noted in comments so the trap is not reintroduced.
