# 2026-10-02 — Rental privacy: real token authentication

## Request
"i want you to make the rentals private only the admin and specific customer can
see their own rent"

## Why the previous fix was not enough
Earlier work scoped `/api/rentals` by a `userId` **query parameter**. That is not
a security boundary: the client asserted its own identity, so anyone could pass
another user's id — or omit it entirely and receive every rental. The single-get,
status, edit and delete routes had no scoping at all.

## The fix — signed tokens (no new dependencies)
Stateless HMAC-SHA256 tokens via `node:crypto`. Format:
`v1.<base64url(payload)>.<base64url(sig)>`, payload `{u, iat, exp}`.

**Key design choice: the token carries ONLY the user id.** Role and customer
scope are re-resolved from the database on every request, so a role change or
deleted account takes effect immediately instead of lingering until expiry.

### New: `src/auth/token.ts`
- `signToken(userId, ttl)` / `verifyToken(token)` / `extractBearerToken(header)`
- `crypto.timingSafeEqual` for signature comparison (no timing leak)
- TTL default 7 days, override with `AUTH_TOKEN_TTL_HOURS`
- **Secret resolution (security-critical):**
  - `AUTH_SECRET` (else `SESSION_SECRET`) if >= 16 chars -> stable across restarts
  - production with NO secret -> generates a **random per-process** secret.
    Deliberately NOT a hard-coded fallback: a default in the source would be
    public and let anyone forge tokens. Trade-off: tokens die on restart, so
    users re-login after a deploy. Set `AUTH_SECRET` to avoid that.
  - development -> fixed fallback so local sessions stay stable

### `src/routes/api.ts`
- `requireAuth` middleware -> verifies bearer token, re-resolves role+scope from
  the DB, attaches `req.auth`. 401 on missing/bad/expired token or dead account.
- `requireRole(...roles)` -> 403 when the role is not allowed.
- Login and register now return `{ token, expiresIn }`.
- New `GET /api/auth/me` — verifies the token and returns the caller (no hash).
- `GET /api/auth/users` now actually enforces the admin-only rule its comment
  already claimed (it previously leaked every user to any caller).

### Rental routes — access model
Matches the frontend `ROLE_ACCESS` map (technician has **no** `rentals` tab):
| Route | Who |
|---|---|
| `GET /rentals` | admin (all) / customer (own only) / technician 403 |
| `GET /rentals/:id` | owner or admin; others get **404**, not 403, so the response does not confirm the id exists |
| `POST /rentals` | admin, or customer — `customerId` is **forced** to their own scope, body value ignored |
| `PATCH /rentals/:id/status` | admin only |
| `PATCH /rentals/:id` | admin only |
| `DELETE /rentals/:id` | admin only |
| `GET /rentals/stats/summary` | scoped for customers (no company-wide revenue) |

Helper `scopeRentalsForAuth()` fails closed: a customer whose scope cannot be
resolved gets `[]`, never the full list. `resolveScopeCustomerId()` maps an
organization-only scope to a real `customers.id` for booking creation.

### `public/js/app.js`
- Token in `localStorage` as `millennium_auth_token`.
- **`window.fetch` wrapper** injects `Authorization: Bearer` for `/api/*` calls
  on the same origin — one change point instead of editing ~40 call sites.
  Skips third-party origins entirely.
- Global 401 handler (except on login/register) clears the token + session and
  returns the user to the sign-in screen.
- `refreshAuthSession()` now uses `/auth/me` (token-verified) instead of the
  unauthenticated `/auth/users`.
- Removed the now-meaningless `userId`/`userRole` query params from the rental
  fetches — identity is no longer client-asserted.
- `handleLogout()` clears the token.

### `render.yaml` / `.env`
- Added `AUTH_SECRET` + `SESSION_SECRET` to `render.yaml` with `sync: false`
  (values go in the Render dashboard, never committed).
- Added a random 32-byte `AUTH_SECRET` to the gitignored `.env`.
- `index.html` asset version -> `20261002a`.

## Verification — 76 tests, all passing
Regression suites live in `tests/` (run from the project root; need the server up):
- `tests/rental-privacy.test.cjs` — **51 passed**. 401 for no/empty/malformed/
  bogus-signature/tampered/expired token; technician 403; admin sees all;
  customer sees only own org; customer 403 on all three mutations; customer
  stats scoped; `/auth/users` 403 for customer and 401 anonymous. Plus a
  **synthetic two-tenant test** (extracted from `dist/`) proving tenant A sees
  zero of tenant B's rows and vice-versa, orphans hidden, fail-closed when no
  scope — since the live DB has only one customer this is how cross-tenant
  isolation is proven without writing to the database.
- `tests/ui-auth.test.cjs` — **16 passed**. Real login form for admin and
  customer, token stored, Rentals tab renders, session survives reload, no page
  errors. Each role runs in its own browser context (a shared page would leak
  localStorage between roles).
- `tests/session-expiry.test.cjs` — **9 passed**. A tampered token on load forces
  re-login; corrupting the token mid-session produces 401 and returns the user
  to the sign-in screen.

## Not done / caveats
- **Devices, tickets and other endpoints still scope by the `userId` query
  parameter** and have the same weakness rentals had (no token required, and
  omitting `userId` returns everything). The `requireAuth`/`requireRole`
  middleware is now available and the frontend already sends the token, so
  extending it is mostly mechanical. Left alone to keep this change reviewable.
- Cross-tenant isolation is proven synthetically, not against two real customers
  — the DB holds one customer org (QCU) and `.kiro/steering/database-protection.md`
  forbids creating test records without an explicit command.
- `customer@gmail.com` / `qcu` are still not in the Registration Mode allowlist.
- Unreferenced leftovers in `app.js`: `openCreateCustomerModal()`,
  `renderDMAllocationTab()`, `deleteCustomerOrg()`.

# 2026-10-02 (2nd) — Rental form layout + customer profile

## Request
"fix the layout of fill up of the rentals also fix the customer profile make it
able to see their profile and edit"

## Root cause of the layout problem
The rental booking modal was built entirely from inline styles that referenced
CSS variables which **do not exist**: `var(--surface-elevated,#1e1e2e)` and
`var(--surface,#15151f)`. The real tokens are `--bg-surface-elevated` and
`--bg-surface`. So every field silently fell back to a hard-coded dark colour.

Consequences:
- In the default dark theme it looked "nearly right" but off-brand.
- In the light theme it was **unreadable**: near-black input backgrounds
  (`#15151f`) with the light theme's dark text (`--text-primary: #0f172a`).
- The modal also had no `max-height`/scroll structure, hardcoded
  `grid-template-columns:1fr 1fr` (no responsive collapse) and no footer.

## Fix — rebuild on the existing design system
`openRentalModal()` and `viewRentalDetail()` were rewritten to use the app's own
classes: `.modal-backdrop`, `.modal-content`, `.modal-header`, `.modal-close`,
`.form-group/.form-label/.form-input/.form-select/.form-textarea`, `.form-row`,
`.btn/.btn-primary/.btn-secondary`. New supporting CSS appended to `style.css`:
`.modal-form` (flex column, `max-height:90vh`), `.form-body` (the only scroll
region), `.form-section` + `.form-section-title`, `.form-hint`, `.modal-footer`,
`.detail-grid`/`.detail-tile`, `.profile-*`.

Also fixed the same broken variables in the rental **filter select** and the
**delete-confirm** dialog, and added `escapeHtml` handling for interpolated
values. `style.css` gained a cache-buster (`?v=`) — it previously had none, so
CSS changes could be served stale.

## Customer profile (new)
- **`PATCH /api/auth/me`** — self-service edit of `fullName`, `email`,
  `location`, plus optional password change. Password change requires the current
  password (verified via `loginUser`). `role`, `organization` and `customerId`
  are **not accepted** — a user cannot widen their own access. Duplicate emails
  and invalid input are rejected.
- Profile dialog: identity header (avatar, name, email, role pill), read-only
  Account section (username, role, organization, member since), Editable Details,
  Change Password. Entry point is the sidebar user chip (now clickable +
  keyboard accessible); the logout button stops propagation.

## Security holes closed along the way
- `POST/PATCH/DELETE /api/auth/users/:id` were **completely unprotected** — any
  anonymous caller could promote themselves to admin, edit or delete any account.
  Now `requireAuth` + `requireRole('admin')`, with guards against an admin
  removing their own role or deleting themselves.
- `db.updateUser()` did `SELECT *` and returned the row: it **leaked
  `password_hash`** and returned **snake_case keys**, so `data.fullName` was
  `undefined` and the UI never reflected a saved profile. Now returns the same
  camelCase shape as `getUsers()`, without the hash.

## Two pre-existing theme bugs found
1. **`<body data-theme="dark">` was hardcoded in index.html**, but `applyTheme()`
   manages the theme on `<html>`. Because `[data-theme="dark"]` matches *any*
   element, body re-declared the dark variables and **pinned all content to dark
   — the light-mode toggle never actually worked on the content.** Removed the
   body attribute; set the initial `data-theme="dark"` on `<html>` instead.
2. The "V2 Dark Canvas Theme Overrides" block has an unconditional
   `body { background-color:#060b19 !important; color:#e2e8f0 }` — it hardcodes
   dark values for both themes. **This is NOT fixed** (it is a large app-wide
   redesign block). Dialogs were instead made self-sufficient by declaring
   `color: var(--text-primary)` on `.modal-content` and friends, so they are
   readable in both themes regardless.

## Verification — 39 new tests, 115 total, all passing
`tests/profile-and-rental-form.test.cjs` (**39 passed**): modal uses the design
system, 5 sections, header/footer/scroll-body, **zero horizontal overflow**,
no input past the modal edge, no leftover `var(--surface,...)`, correct colours
in **both** themes (white bg / dark text / dark readable title in light mode);
profile opens, lists 4 account fields, saves an edit (server + chip + session),
restores the original value, and rejects role escalation, org changes, wrong
current password, bad email, short password, and unauthenticated requests.
Regression: rental-privacy 51, ui-auth 16, session-expiry 9 — all still pass.

Screenshots: `screenshots/` (7 files, both themes, customer + admin views).
Test scripts: `tests/*.test.cjs`, `tests/capture-screenshots.cjs`.
Asset versions: `style.css?v=20261002b`, `app.js?v=20261002b`.

## Notes
- The profile test writes once (fullName) and restores the original value, so
  the database is left exactly as found. Verified: `orgen` fullName is "Customer".
- The password hash is a **weak non-cryptographic djb2-style function**
  (`MHASH_<hex>`), not bcrypt/argon2. Changing it would invalidate every existing
  password, so it was left alone — but it should be migrated to a real KDF.
- Still open: devices/tickets scope by the old `userId` query param.

# Showcase feature removed (user: "remove the showcase i dont need this")

The user pointed at the in-app **Millennium SmartBoard Hardware Showcase** page
and asked for it to be removed. It is now gone from the app.

## What was removed
- **`public/js/app.js`** — deleted the entire self-contained block of **1825
  lines** (old lines 1323–3147): the whole *Interactive SmartBoard Simulator*
  engine (theater / whiteboard / Windows 11 / Android 13 demo modes, all the
  "cool motion gesture" animations, feature-demo tour, stylus + dongle state)
  plus `renderMillenniumShowcase()` and `renderShowcaseView()`.
  Also removed:
  - `'showcase'` from all three `ROLE_ACCESS` arrays.
  - `case 'showcase':` from the `renderApp()` tab switch.
  - the two `setTimeout(initSmartBoardSimulator, 50)` calls (dashboard + default)
    and `initSmartBoardSimulator()` itself.
  - the orphaned simulator state block in `const state` (`simulatorMode`,
    `theaterState`, `windowsState`, `androidState`, stylus/dongle/demo fields).
  - the two `onclick="navigateTo('showcase')"` handlers on the dashboard hero
    (`.hero-display-wrapper`, `.hero-right-accent`) — **markup kept**, only the
    click + `cursor:pointer` + tooltip removed.
- **`public/index.html`** — removed the sidebar promo card
  (`.sidebar-promo-card`, the "Millennium / Smart Interactive Board ›" thumb
  card) whose only purpose was to link to the showcase. The
  `.sidebar-banner-box` below it was kept.

## Deliberately kept
- **The login screen's marketing panel** (`.auth-showcase-panel`,
  `.auth-showcase-footer-bar`) — it is login-page branding, not the showcase
  page, and removing it would gut the login screen. Flagged to the user.
- **The showcase CSS** (~1000 lines in `style.css`) — now dead but invisible,
  and its blocks are interleaved with login-panel rules that share the
  `auth-` prefix, so removal was judged higher-risk than the payoff.

## Why the cut was safe
`initSmartBoardSimulator` was called from `case 'dashboard'` and `default`, so it
looked like a dashboard dependency. It is not: the only `.board-viewport` markup
in the whole app lived inside `renderMillenniumShowcase()` (old line 2222), and
the dashboard hero is just an `<img>`. After the cut, grep confirmed **0**
remaining references to any simulator function or state field.

Deep-linking to the removed tab is harmless: `renderApp()` already redirects a
tab not present in `ROLE_ACCESS` to `ROLE_META[role].defaultTab`.

## Verification — 40 new tests (155 total), all passing
New `tests/showcase-removal.test.cjs` (**40 passed**) runs real headless Chrome
for admin / technician / customer:
- no `[data-tab="showcase"]` nav item, no `.sidebar-promo-card`, no "showcase"
  wording anywhere in the app shell, `ROLE_ACCESS` excludes it
- `renderShowcaseView`, `renderMillenniumShowcase`, `initSmartBoardSimulator`
  are all `undefined`
- `navigateTo('showcase')` redirects to the role default tab with no blank
  screen and no page error
- dashboard hero markup still present, no showcase link, cursor no longer
  `pointer`, dashboard still renders KPI cards and the hero image
Regression: rental-privacy 51, ui-auth 16, session-expiry 9,
profile-and-rental-form 39 — all still pass.
Screenshots: `screenshots/8-dashboard-admin-dark.png`,
`9-dashboard-admin-light.png`, `10-sidebar-customer-light.png`,
`11-login-screen.png`.

`public/` is served statically, so no rebuild was needed.

# Public landing page / new-user guide (user request)

User asked for a **landing page** with four sections — **Features, How it works,
User roles, About** — usable as a guide for new users, and explicitly:
**"i want it scrollable not fixed"**. Their reference screenshot was a phone view
of `futuretrack-sti.com`: a top bar, an in-page nav (Features / How it works /
User roles / About), a "Get started" button, then role cards with coloured left
rails and bullet lists.

## What was built
- **`public/landing.html`** (new, ~700 lines, self-contained).
  Deliberately does **not** load `/css/style.css` — that file contains a global
  `body { background:#060b19 !important }` override (see the earlier notes) that
  would fight a landing page. Own `<style>` block with its own light/dark token
  sets instead.
  Sections: hero → `#features` (11 feature cards) → `#how-it-works` (5 numbered
  steps) → `#user-roles` (3 role cards) → `#about` (copy + at-a-glance spec card)
  → gradient CTA → footer.
- **`src/server.ts`** — added `app.get('/landing', ...)` **before** the SPA
  catch-all. This was essential: the catch-all `app.use()` serves `index.html`
  for any unmatched path, so without an explicit route `/landing` would have
  silently rendered the app shell instead of the guide.
- **`public/index.html`** — added a "New here? See what every feature and role
  does →" link (`.auth-guide-link`) to the bottom of the sign-in card.
- **`public/css/style.css`** — added the `.auth-guide-link` rules next to
  `.auth-register-link`.

## "Scrollable, not fixed" — how it is enforced
- The header is plain in-flow markup: **no `position:fixed`, no `position:sticky`
  anywhere on the page** (verified by walking every element and reading computed
  `position`).
- The reference's nav was a fixed overlay panel with a close button; this
  implementation has no overlay at all.
- Anchor links use JS smooth-scroll with a header-height offset instead of CSS
  `scroll-behavior` alone, so sections land correctly despite the in-flow header.
- Content is accurate to the real app: role capabilities come from `ROLE_ACCESS`
  (admin = 11 modules, technician = devices/tickets/inventory, customer =
  devices/tickets/customer-portal/rentals), and default landing tabs come from
  `ROLE_META`.

## Layout bug found and fixed
First render wrapped the hero headline onto **3 lines** — "Everything you need /
to / run your SmartBoards". Measured in the browser: the h1 column was 565px
while the natural width of line 1 was **604px**. Fixed by widening the hero text
column (`1.05fr/.95fr` → `1.15fr/.85fr`) and lowering the clamp
(`clamp(2.1rem,5vw,3.5rem)` → `clamp(1.8rem,4.2vw,3.25rem)`).
Verified at 1440/1280/1100/1024/390/360px: **2 lines everywhere, 0px overflow**.
Mobile header also trimmed (`.brand-sub` hidden, smaller logo/CTA) so brand +
theme toggle + CTA share one row instead of wrapping to three.
