### 2. New chart primitives (no new dependency)
No chart library in the project — the admin dashboard hand-builds an SVG donut.
Added four reusable helpers in `app.js` next to the other dashboard helpers:

| helper | use |
|---|---|
| `donutChart(segments, centerValue, centerLabel, opts)` | multi-segment SVG donut + legend |
| `barChart(rows, opts)` | horizontal bars, scaled to the **max** value |
| `proportionStrip(segments)` | one-line stacked mix + key |
| `chartPanel(title, subtitle, body, action)` | card shell matching `.rec-section` |

**Do not reuse the older `.donut-*` admin rules** (style.css ~7588): they
hard-code `color: #fff` and `background: #060b19`, so the admin donut is
unreadable in light mode. The new components take every colour from CSS custom
properties. Palette lives in `--chart-c1..c8`, set **twice** — dark uses lighter
siblings of the same hues, because the light values fall under 3:1 on the dark
card.

Arc geometry: each segment is a full circle with an explicit
`stroke-dasharray: len 100-len` and a `stroke-dashoffset` from the running total,
so adjacent segments butt exactly instead of accumulating rounding gaps. A
zero-value slice draws no arc but **stays in the legend** — "Offline 0" is
information.

### 6. Fixed a flaky contrast check in `role-dashboards`
After my changes it failed intermittently (~1 run in 3), always on a **random
one of the six** colour selectors — the signature of a race, not a regression.
Cause: the suite did `applyTheme()` then `sleep(250)`, but the stylesheet
transitions `background-color`/`color` over **0.25s**, so it measured a blend of
the old and new palettes. Invalidated by reading the computed `color` +
`backgroundColor` twice 50ms apart and requiring them to match (up to 60 tries).
**5/5 consecutive runs green afterwards.** Verified the page itself was always
correct — this was purely a measurement-timing bug.

## Correction — the admin dashboard is NOT light-mode broken
I flagged this in the previous session's summary and it was **wrong**. Checked
before changing anything: in light mode the admin dashboard renders correctly —
`.donut-center-text strong` computes to `rgb(15,23,42)` on white, `.donut-legend`
to `rgb(71,85,105)`, `.widget-card` to white. The hardcoded `color: #fff` /
`background: #060b19` at style.css ~7611, ~7635, ~7667, ~7717 are **overridden
by later light-mode rules**, so they never win the cascade. Same for
`.stock-gauge-circle strong` (#7767) and `.client-chip`. Only `.badge-red-sm`
(#7779) legitimately keeps `#fff` — it sits on a red background.

Lesson: a hardcoded hex in the stylesheet is not proof of a rendering bug. Compute
the effective style, or screenshot it, before "fixing" a specificity shadow.

### Two chart-helper refinements
1. **`barChart(rows, { showShare: true })`** — new option appending each row's share
   of the total. Max-scaling (kept: it stops one dominant value flattening the rest)
   makes two equal values both render full-width, which reads as "both maxed". The
   admin priority chart hit exactly this (High 1 / Medium 1 → both 100%), so the
   "· 50%" suffix is what makes equal bars interpretable.
2. **Bar radius capped at 4px** (was `999px`). A full pill on a 12%-wide fill turned
   "AV Equipment" into a detached capsule instead of a bar. `min-width: 4px` stops a
   tiny value vanishing entirely.

Also gave `.prop-strip .prop-seg:only-child` a full radius — a single-segment strip
(Schools 3, Corporates 0) otherwise showed squared-off ends.

### Checked and NOT a bug

  + the track's own background; fills are correctly clipped by `overflow: hidden`.
  Verified by measuring `fill.getBoundingClientRect().width` against `trackW`.
