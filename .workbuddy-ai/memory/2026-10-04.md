## Entry points: `/` is now the landing page, the dashboard moved to `/app`

User: *"i want to go it first to landing page when someone opening the link"*.
Previously `express.static` answered `/` with its default directory index
(`index.html`), so the link opened the dashboard sign-in portal and the landing
page was only reachable at `/landing`.

### `src/server.ts` — order is the whole trick
Added two explicit routes **before** `app.use(express.static(publicPath))`:

| URL | Serves |
|---|---|
| `/` | `public/landing.html` |
| `/app` | `public/index.html` |
| `/landing` | `public/landing.html` (alias — the sign-in screen links here) |

Declaring `/` after `express.static` would do nothing: static's directory index
wins. `/app` has **no trailing slash** on purpose — with one, the shell's
root-relative asset URLs would resolve under `/app/` and break every stylesheet.
The SPA catch-all still serves `index.html` for unknown paths (the app has no
client-side URL router), and the `/api` 404 handler still sits before it.
`npm run build` required (TypeScript); `public/**` needs none.

### The links that would have silently looped
- `public/landing.html` — 4 CTAs (`Get started` ×3, footer `Sign in`) were
  `href="/"` and would have reloaded the landing page. Repointed to `/app`.
  The brand logo stays on `/` (it is the home link).
- `public/manifest.json` — `start_url` and all three `shortcuts` were `/`
  (`/?tab=…`, which `app.js` never read — it has no `location.search` handling,
  so those were dead anyway). Now `/app`.

### 21 navigations across 15 test files
Every suite reached the dashboard via `page.goto(BASE)` / `goto(BASE + '/')`;
those now land on the landing page. Added `const APP = BASE + '/app';` to each
file and repointed them with two `goto(`-anchored regexes —
`/(\w+)\.goto\(BASE \+ '\/',/` and `/(\w+)\.goto\(BASE,/`. Anchoring on `goto(`
is what keeps `fetch(\`${BASE}/api/...\`)` from being corrupted to `APPapi/...`;
verified afterwards with a corruption grep. `/landing` navigations were left
alone. The throwaway migration script was deleted after the run.

### Verification
All 10 suites green — **387 checks**: landing-page 54, mobile-responsive 67,
tickets-layout 32, rental-privacy 74, showcase-removal 40,
profile-and-rental-form 39, no-refresh 32, theme-switch 24, ui-auth 16,
session-expiry 9. Routes confirmed by title: `/` → "Getting Started…",
`/app` → "Millennium SmartBoard Management System…", `/landing` and
`/landing.html` → the guide, `/index.html` → the shell, and `/` serves 4
`href="/app"` links.

### Two failures that were NOT the change — Chrome + Google Fonts DNS
`landing-page` failed "no page errors" with three `ERR_NAME_NOT_RESOLVED`, and
`no-refresh` died on a **`waitUntil: 'networkidle0'` navigation timeout**
(line ~231). Both files load `fonts.googleapis.com` (`index.html:56`,
`landing.html:36`), and a *hanging* font request means the network never goes

**Rerun before investigating.**

## Restock Shipment dialog rebuilt on the system's dialog shell

User: *"fix the ui of this and design make it alligned to the design of the
system"*, with a screenshot of the Restock Inventory Shipment modal.

### Root cause — an undefined token, not a styling choice
The dialog card was `background: var(--bg-card, #1a1a2e)`. **`--bg-card` is
defined nowhere in `style.css`**, so the fallback always won and the card was a
hard-coded dark navy in *both* themes. Everything inside it used real tokens
(`.form-input`, `.btn-secondary`, `--text-primary`), which is why the screenshot
looked like a light-mode form poured into a dark box.

The giveaway that the app was in **light** mode: the title used
`color: var(--text-primary)` = `#0f172a` and was **invisible on the dark card**,
while the inputs were white and the tabs gradient-filled — all light-theme
values. `--primary-gradient` is a deep blue in light mode but bright cyan in
dark, so the gradient pills also identified the theme.

Three sibling dialogs had the identical defect: `openCreateUserModal`,
`openEditUserModal`, `openCreateCustomerModal`. And a fourth use,
`background: var(--bg-card)` with **no** fallback, was silently dropping the
whole declaration (transparent panel in a rental view).

### Fix
- `openRestockModal()` rewritten onto the shared shell: `.modal-backdrop` +
  `.modal-content.modal-form`, `.modal-header` / `.modal-title` / `.modal-close`,
  a `<form>` with `.form-body`, `.form-section` + `.form-section-title`,
  `.form-group` / `.form-label` / `.form-input` / `.form-select`, and
  `.modal-footer`. Zero inline hexes left. Added `closeRestockModal()`, the
  `requestAnimationFrame(() => overlay.classList.add('active'))` show, Escape
  handling and a real click-outside handler.
- New `.seg-tabs` / `.seg-tab` segmented control replaces the two buttons that
  swapped `.btn-primary` / `.btn-secondary` — that made an *inactive* tab read as
  a primary action, and it was separated by a hard-coded
  `rgba(255,255,255,0.08)` rule invisible in light mode. `toggleRestockMode()`
  now toggles `.is-active` + `aria-selected`.
- New `.form-error` (uses `--accent-rose-text`; `#f43f5e` is a *fill* colour at
  ~3.8:1 as small text) and `.form-stack`.
- The other three dialogs: container → `class="modal-content"` (theme-aware
  surface/border/radius/shadow), error divs → `.form-error`, scrim aligned to
  `rgba(15,23,42,0.65)` + `blur(8px)`.
- Asset version `?v=20261004b`.

### A real contrast bug the test caught
`.seg-tab.is-active` first used `background: var(--primary-gradient); color:#fff`
to mirror `.btn-primary`. The dark-theme gradient is **bright cyan**, so white
text on it measures **1.4:1**. Changed to a *tinted* pill — `--primary-light`
background, `--primary-hover` text, `--primary` inset ring — which measures
>= 6:1 in both themes and also stops the tab from looking like the submit button.
(`--primary` alone is 3.9:1 on `--primary-light` in light mode, hence
`--primary-hover`.) Note `.btn-primary` itself is still white-on-bright-cyan in
dark mode — pre-existing and app-wide, not touched.

### New suite: `tests/modal-theme.test.cjs` — 63 checks
Measures **rendered** luminance and WCAG contrast (with source-over alpha
compositing) in both themes, so a one-theme fix cannot pass. Covers the dialog
surface, title, labels, section panel, segmented control (active/inactive,
contrast, "is not a `.btn-primary`", "is not a gradient"), footer, tab
switching, Escape, click-outside, Cancel, the other two dialogs in light mode,
and source checks that `--bg-card` / `#1a1a2e` are gone.

### Phantom bug worth remembering
The first screenshots showed a **transparent dialog** — the inventory cards
behind it plainly visible. `getComputedStyle` reported opaque white and every
colour assertion passed. Cause: `.modal-backdrop` fades in over 0.25s, and the
screenshot was taken immediately after `openRestockModal()`, mid-fade. Fix:
inject `*, *::before, *::after { transition: none !important; }` **before**
opening, then sleep 300ms before `page.screenshot()`. Added a real assertion
that the backdrop's computed `opacity` is `1`.

## Landing page: scroll-motion system + visual polish

User: *"add animation when scrolling in landing page also enhance the ui design
of landing page make it more attractable and proffesional when im scrolling its
showing animation"*.

Before: one `.reveal` (fade up 18px, 0.6s) firing on every block at the same
instant, no keyframes anywhere, `IntersectionObserver` at
`rootMargin: '0px 0px -8% 0px'`.

### Motion
- **Direction variants** — `reveal-up` / `-down` / `-l` / `-r` / `-zoom` /
  `-soft`, each carried *alongside* `.reveal` so one `.reveal { opacity:1 }`
  override still neutralises all of them (the screenshot harness depends on
  that). `.reveal.in` resets `transform` and wins on specificity, so no
  `!important`. Easing switched to expo-out (`--ease-out`) — the motion
  decelerates into place instead of easing in and out.
- **Derived stagger**: `--d` is computed from each element's index among its
  `.reveal` siblings (capped 480ms), so grids cascade with no per-card markup
  and a lone section heading still fires immediately.
- **Reading-progress bar** as `.site-head::after`, `transform: scaleX(--sp)`.
  It is `position: absolute`, **not fixed** — the page has exactly one pinned
  element and `landing-page.test.cjs` asserts nothing else is fixed/sticky.
- **Parallax**: `--sy` drives `.hero-visual` (-0.05) and the three aurora blobs
  (+0.10 / +0.17 / +0.06).
- **One rAF-throttled handler** writes `--sp` and `--sy`. The custom properties
  are set on `.site-head` / `.aurora` / `.hero-visual` — **never on `:root`**,
  which would invalidate the computed style of the entire tree every frame.
- **Header condenses** (`18/14` → `11/9` padding) once `.is-stuck`.
- **Hero load animation** (`.hero-copy > *`, staggered `heroIn`) rather than a
  reveal — above the fold, so it must not depend on the scroll observer. Only
  `opacity` is animated on `.hero-visual`; its `transform` belongs to the
  parallax and the two would fight.
- **Stat count-up** via `data-count` / `data-suffix`, zeroed before first paint
  so there is no flash of the final number then a jump down. Real values stay in
  the HTML as a no-JS fallback.
- **Feature spotlight** following the cursor (`--mx`/`--my`), gated on
  `(hover: hover)`, needing `.feat { isolation: isolate }` so the `z-index:-1`
  pseudo lands above the card background but below the copy.
- Polish: animated sheen on the gradient headline, hero scroll cue, gradient
  rail that grows on `.step:hover`, `.feat-ico` lift, stat hover colour, soft
  gradient washes on the `.band-alt` edges, drifting glow on `.final-cta`.

### Real bug found — the footer could never reveal
The observer's `rootMargin: '0px 0px -8% 0px'` inset is a **percentage of the
viewport**. On a 900px-tall window that excludes the bottom 72px, but
`.foot-inner` is only ~50px tall — so it sat permanently inside the excluded
band and stayed at `opacity: 0` **forever**. No error, no visual clue until the
new suite scrolled the whole page and reported
`foot-inner opacity=0 in=false rect=832..882 vh=900`. Fixed with
`revealRemaining()`, which force-reveals whatever is left once
`innerHeight + pageYOffset >= scrollHeight - 2`. General rule: a percentage
bottom inset is only safe when every observed block is taller than that
percentage of the viewport.

### Also had to neutralise sideways entrances below 1240px
`.wrap` is 1180px with 24px inner padding, so below that width the padding is
the only slack and a 38px `-l`/`-r` offset would poke past the viewport edge
(and `landing-page.test.cjs` asserts `realOverflow <= 0`). `≤1240px` makes them
vertical; `≤720px` makes everything vertical and kills the parallax.

### New suite: `tests/landing-motion.test.cjs` — 40 checks
At-rest state (hidden blocks really hidden, bar absolute + zero-length, only the
header pinned), stagger order + cap, scroll behaviour (`.is-stuck`, bar length
tracks and grows, header condense, parallax vars + real translateY), reveals
settling to `opacity:1`/`transform:none`, **a full scroll pass leaving nothing
invisible**, the spotlight, `prefers-reduced-motion` (visible immediately, bar
removed, stats instant) and mobile 390 (vertical entrances, no overflow, no
parallax, bar still tracks, header ≤130px). Also had to fix one of my own
assertions — the first `.sec-head` is legitimately already in view at 1440×900,
so the "starts hidden" check now uses `.final-cta`.

### Results
landing-motion 40/0 (new), landing-page 54/0, mobile-responsive 67/0. Full set
now **490 checks**. `landing.html` carries `no-cache` meta tags, so no `?v=`
bump was needed.
