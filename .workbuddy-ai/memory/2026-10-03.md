## Landing page: header made sticky (user follow-up)

Previous session built `public/landing.html` with an explicitly **non-fixed**
header, because the original request said "i want it scrollable not fixed".
The user then sent a screenshot of the header and asked: **"fix this make it
still visible even i scroll"** — i.e. they wanted the *content* scrollable (not
a fixed overlay menu blocking it), but the **nav bar pinned**. So the header is
now `position: sticky`.

### The non-obvious blocker
`body` had `overflow-x: hidden` (added to stop a stray horizontal scrollbar).
**`overflow-x: hidden` on `<body>` turns the body into a scroll container and
silently breaks `position: sticky` on descendants** — the header just scrolls
away and it looks like the CSS was ignored.

Fix: use **`overflow-x: clip`** instead. `clip` still clips the overflow but
does *not* create a scroll container, so sticky keeps working. (Browser support
is fine: Chrome 90+, Firefox 81+, Safari 16+.)

### Changes in `public/landing.html`
- `body`: `overflow-x: hidden` → `overflow-x: clip` (with a comment explaining
  why, so nobody "tidies" it back).
- `.site-head`: `position: relative; z-index: 2` → `position: sticky; top: 0;
  z-index: 50`, plus `background: var(--header-bg)` and
  `backdrop-filter: blur(16px) saturate(1.7)` so content is legible passing
  underneath. `.site-head.is-stuck` adds the hairline border + shadow.
- `section { scroll-margin-top: 28px → 96px }` to clear the pinned header.
- JS: hoisted `var head` out of `scrollToSection`, added a passive scroll
  listener toggling `.is-stuck` at `pageYOffset > 8`, and clamped the anchor
  scroll target at 0.
- Added the same `no-cache` meta tags `index.html` uses, so iterating on this
  page does not serve a stale copy.

### Verification — 41 tests (was 33), all passing
`tests/landing-page.test.cjs` updated to assert the *new* contract:
- the header **is** `position:sticky`; **nothing else** on the page is
  fixed/sticky (so no overlay sits on top of the content)
- the header is on screen at every scroll depth (0 / 400 / 1400 / 3200 / bottom),
  pinned at `top === 0`, and gains `.is-stuck` only once scrolled
- content genuinely passes underneath it
- mobile 390×844: header stays visible, pinned height ≤ 130px

**Test-writing gotcha:** the page has CSS `scroll-behavior: smooth`, so
`window.scrollTo(0, y)` is still animating when the assertion reads
`pageYOffset` — this produced a false failure (read 56 instead of 0). Use
`window.scrollTo({ top: y, behavior: 'instant' })` in probes to override it.

Screenshots: `screenshots/22-landing-sticky-header-dark.png` (desktop, pinned
over scrolled content), `19-landing-mobile-scrolled.png` (mobile, pinned).
App untouched this turn — `/`, `/health`, `/landing` all still 200.

# Mobile support for the app (user: "make it this website mobile support")

The landing page was already mobile-clean (0px overflow), so the real work was
the **app itself**. Two bugs, one of them critical.

## Bug 1 (critical) — a phone user could not sign in at all
On a 390px phone the sign-in screen laid out at **551px** wide. The submit
button sat entirely off-screen, so nobody could log in. The audit only found it
because logging in *failed* — the first `page.click('#loginSubmitBtn')` threw
"Node is either not clickable or not an Element".

Root cause: the auth layout is a flex chain
(`.auth-portal-overlay` → `.auth-portal-frame` → `.auth-split-layout` →
`.auth-showcase-panel` + `.auth-portal-card`). The card had a hard `width:410px`
and **none of the children declared `min-width: 0`**, so they could not shrink
below their min-content width. There were already `@media (max-width: 992px)`
and `640px` rules trying to stack it, but they were powerless without
`min-width: 0`.

Fix in `public/css/style.css`: rewrote the 992px and 640px auth blocks —
`min-width: 0` on every link in the chain, single column, full-bleed frame
(`border-radius:0`, `clip-path:none`), and at ≤640px the decorative
`.auth-showcase-panel` is hidden outright (it pushed the form below the fold;
the brand is still in the top nav and the card links to `/landing`).

## Bug 2 — the app header forced the document to ~565px
Hiding `.app-header` dropped `document.scrollWidth` from 565 → 390, which
pinned it exactly. The header packs a hamburger, a full brand block, a search
field, a notification button and a user chip into one non-wrapping flex row.
Fixed with new rules at the end of `style.css`: hide `.brand-text-container`
and `.auth-user-info` on phones, let the search field shrink (`min-width: 0`),
and `--header-height: 62px` at ≤640 (that variable also drives the off-canvas
sidebar's `top`, so the drawer still meets the header exactly).

## Landmine found: CSS defined later beats the media queries
`public/css/style.css` has the **base `.app-header` rule at line ~6452, which
appears AFTER the responsive rules at 5752 / 5800 / 6008**. At equal
specificity the later rule wins, so all of those `@media` overrides for the
header were dead code — including `height: auto` and `height: 50px`. The base
also hardcodes `height: 74px` rather than using `var(--header-height)`.
Consequence: **any new responsive override for the header must be appended at
the END of the file.** All of this session's mobile CSS was appended there for
that reason. The same hazard likely affects other components whose base rules
live in the 6400+ block — worth auditing before trusting an existing
`@media` rule anywhere in this file.

## Also fixed
- **Analytics was unreadable on a phone**: its two panels used an *inline*
  `style="display:grid;grid-template-columns:1fr 1fr"`. Inline styles beat every
  stylesheet rule, so it could never be made responsive. Converted to a
  `.analytics-grid` class. Same treatment for the Data Manager allocation form
  (`1fr 1fr auto` → `.alloc-form-row`). Both collapse to one column at ≤900px.
- `.kpi-v2-footer` (dashboard KPI cards) is a nowrap space-between flex row —
  the label and trend badge collided at two-cards-per-row. Now wraps.
- `.data-table-wrapper` got `min-width: 0` so wide tables scroll *inside* their
  card instead of widening the page.

## The measurement insight that made this debuggable
With puppeteer mobile emulation (`isMobile: true`), when content is wider than
the device **Chrome widens the layout viewport to fit it**, so
`scrollWidth - innerWidth` stays ~0 and the usual overflow check passes while
the page renders zoomed-out and cut off. `window.innerWidth` was **579 on a
390px device**.

The reliable assertion is therefore: **`window.innerWidth === deviceWidth`**.
That single check is what exposed both bugs. Assert it for every device in
`tests/mobile-responsive.test.cjs`.

## Verification — 60 new tests (256 total), all passing
New `tests/mobile-responsive.test.cjs` (**60 passed**), covering
390/360/414/768px:
- sign-in card, role tabs and **submit button** all on screen; viewport never
  expands
- a phone user can genuinely sign in (token stored, overlay hidden, dashboard
  renders)
- header fits one row, hamburger visible, brand collapsed, chip = avatar only,
  ≤70px tall
- drawer opens off-canvas → on screen, dimming overlay present, closes again
- all 11 admin views render with the viewport still at 390px
- table wrapper scrolls inside its card
- customer role + landing page at every device width
Regression: rental-privacy 51, ui-auth 16, session-expiry 9, showcase-removal 40,
profile-and-rental-form 39, landing-page 41 — all still pass. Desktop re-checked
directly: analytics still 2 columns, allocation row still 3 columns, no overflow.

Screenshots: `screenshots/mobile-audit/` (login at 4 sizes, every view at 390px,
sidebar open, desktop analytics).

# Mobile drawer: nav items were untappable (user: "fix the nav menu i cant click the other options")

Follow-up to the mobile work above. After the responsive pass, the user sent a
screenshot of the open drawer with the dashboard visible behind it: the menu
rendered fine but **tapping any nav item did nothing**.

## Diagnosis
`document.elementFromPoint()` at the centre of each of the 7 nav items returned
either `div.mobile-backdrop` (z 998) or `div.sidebar-overlay` (z 98) — never the
`.nav-item` itself. A real `page.click()` therefore landed on the overlay.

That looked impossible: `.app-sidebar` carried `z-index: 999`, well above the
overlay's `98`. Walking the ancestor chain found the answer —
**`.app-container { position: relative; z-index: 1 }` creates a stacking
context.** The sidebar lived inside it, so its `999` only ranked *within*
`.app-container`; as a whole that container sat at `z-index: 1` in the root
context, and the overlay was a direct child of `<body>` at `98`. The overlay
painted above the entire container subtree. **No z-index value on the sidebar
could ever fix this** — it was a context problem, not a number problem.

## Fixes
- `public/index.html`: moved `.sidebar-overlay` from `<body>` level to **inside
  `.app-container`**, immediately before `<aside class="app-sidebar">`, so
  sidebar and overlay now compete in the same stacking context.
- `public/js/app.js`: `toggleMobileMenu()` and `closeMobileMenu()` now delegate
  to `toggleMobileSidebar()` instead of creating a body-level `.mobile-backdrop`
  (one drawer mechanism, not two). The old backdrop was the *other* thing eating
  the clicks, so removing it was half the fix.
- `public/css/style.css`: appended a drawer block at end of file — base
  `.sidebar-overlay { display: none }`, and at ≤900px `z-index: 98` with
  `.app-sidebar.mobile-open { z-index: 999 }` (now effective, same context).

## Second, independent bug — the drawer never closed on tap
The auto-close listener bound `document.querySelectorAll('.tab-btn')`, **a class
that does not exist** in the sidebar (the items are `.nav-item`), so it matched
nothing. Rewritten to bind `.app-sidebar .nav-item`, and the resize threshold
corrected 767 → 900 to match the CSS breakpoint. Without this the drawer stayed
open after navigating even once the clicks worked.

## Verification
`tests/mobile-responsive.test.cjs` extended to **67** (was 60) with drawer
regression checks: `overlayParentIsContainer`, `sidebarZ > overlayZ`, all 7 nav
items being the topmost element at their centre ("ALL CLICKABLE"), a real
`page.click()` landing on a nav item, navigation actually occurring, and the
drawer auto-closing. After a real tap on Inventory:
`{"tab":"inventory","drawerOpen":false,"overlayActive":false,"overlayDisplay":"none","innerWidth":390}`.

Full regression re-run — **263 passed, 0 failed**:
mobile-responsive 67, rental-privacy 51, ui-auth 16, session-expiry 9,
showcase-removal 40, landing-page 41, profile-and-rental-form 39.
Desktop re-checked at 1440/1100/900/768: sidebar 250px, side-by-side, overlay
`display: none`, unaffected.
Asset versions bumped to `style.css?v=20261003f`, `app.js?v=20261003f`.

**Lesson worth keeping:** when a `z-index` appears to be ignored, look for a
stacking context on an ancestor (`z-index`, `transform`, `filter`, `opacity`)
before touching the number. And verify tap targets with `elementFromPoint()`,
not a screenshot — the screenshot of this bug looked completely normal.

# "the website is refreshing" — four separate causes

User: *"i see the website is refreshing can you fix it? i dont want to see like
its refreshing"*. Measured rather than guessed, and it turned out to be **four
independent artifacts**. A screenshot at 60 ms after navigation was the thing
that made the first one undeniable.

## 1. The sign-in portal was painted then removed on every load
`.auth-portal-overlay` is a full-screen (`position: fixed; inset: 0;
z-index: 9999`) login portal with a background photo, and it is **visible by
default** in `index.html` — no inline `display:none`. It was only hidden by
`hideAuthOverlay()` *after* `await refreshAuthSession()`, i.e. after a network
round-trip to `/auth/me`. A screenshot taken 60 ms into the load showed the
whole login screen; by 260 ms it was gone. That is the "refresh".

Fix — a small **inline script in `<head>`, before any stylesheet** (so it runs
before the first paint), which tags `<html>` with `.boot-has-session` when a
token is already in `localStorage`. CSS then keeps the portal off screen from
frame one:

```css
html.boot-has-session .auth-portal-overlay { display: none; }
```

`app.js` removes the class the instant the real session state is known, in the
same task as the `hideAuthOverlay()`/`showAuthOverlay()` call, so no frame is
painted in between and a rejected token still falls back to the portal.

## 2. The saved theme was applied after first paint
`<html lang="en" data-theme="dark">` is hardcoded, but `initTheme()` only ran on
`DOMContentLoaded` — long after the first paint. A user with **light** saved
therefore saw dark, then light. The same inline boot script now applies the
theme synchronously, before the stylesheet, so the first styled frame is already
correct. (`applyTheme` still runs later and is now a no-op visually.)

`public/landing.html` had the identical bug, only worse: its theme script sits at
the **bottom of the body** (line ~885), so the entire dark page painted before
flipping to light. It now has the same before-the-stylesheet boot script.

## 3. The 30-second telemetry poll rebuilt the whole view
`setInterval(() => fetchAllData(), 30000)` → `fetchAllData()` → `renderApp()`
→ `mainContent.innerHTML = renderXView()`. A **wholesale DOM replacement** every
30 seconds: scroll reset, CSS animations restarted, images re-fetched. Proved it
by tagging an existing node with a JS property and watching it vanish.

Fix: the poll now runs `fetchAllData({ silent: true })`. A background poll whose
data has not changed **does not touch the DOM at all**.

**The trap here:** the obvious guard — compare the freshly generated HTML with
`mainContent.innerHTML` — does **not work**. `innerHTML` returns the
*serialised* DOM, which does not round-trip byte-for-byte with the template
string (attribute quoting, self-closing tags, entity escaping), so it reports a
difference even for logically identical markup. Compare the **source data**
instead: `dataSignature()` hashes the state collections.

`state.notifications` had to be excluded from that signature. The server
reshuffles it on every poll (same length, different content), so including it
made the signature differ every single time and the short-circuit never fired.
It only feeds the header bell (`renderNotifications()` → `#notifBadge`/
`#notifList`), never `#mainContent`, and the bell is still updated on every poll.

The dashboard also renders a live clock (`new Date()` → the "Oct 3, 2026
Saturday, 02:07 AM" chip). Since the poll no longer re-renders, the clock got an
id and a tiny `updateDashboardClock()` updates those two text nodes in place.

## 4. Logout did a real page navigation
`handleLogout()` did `window.location.href = '/'` after a 1.2 s toast — a
genuine full reload of every asset. Now it resets in place: clears the token and
session, drops every cached collection (so the next user cannot see the previous
one's rows), empties `#mainContent`, resets the nav/role/chip, clears the sign-in
form, and calls `showAuthOverlay()`. Also clears `lastDataSignature` and any
in-flight `ticketChatPollInterval`. Verified a re-login works straight after.

## Verification — new suite `tests/no-refresh.test.cjs`, 32 checks
- signed-in load: the portal is **never** visible in any frame where the
  stylesheet is in effect (`cssReady` guard, so the pre-CSS default `block` is
  not counted as a flash)
- light theme saved: **no frame is ever dark**, and the first styled frame is
  already light — asserted for both `/` and `/landing`
- signed out: portal visible, no boot class, form on screen
- **rejected token**: portal comes back and the boot class is handed back
- 30s poll: the tagged node survives, the clock is still populated
- logout: JS context survives (`window.__logoutProbe` intact), zero main-frame
  navigations, token cleared, portal back, form reset, re-login works
- static guards: no `location.reload()`, no `window.location.href =` in `app.js`

Full regression — **295 passed, 0 failed**: no-refresh 32, mobile-responsive 67,
rental-privacy 51, ui-auth 16, session-expiry 9, showcase-removal 40,
landing-page 41, profile-and-rental-form 39.
Asset versions bumped to `style.css?v=20261003h`, `app.js?v=20261003h`.

Screenshots: `screenshots/no-refresh/` — at 70 ms the **app shell** is on screen
instead of the login portal; `light-t70.png` is already light.

**General lesson:** a "the page is refreshing" complaint is usually not one bug.
Sample the first ~500 ms of the load with a `requestAnimationFrame` recorder
installed via `evaluateOnNewDocument`, and separately tag a DOM node with a JS
property to detect teardown — both are cheap and both produced the answer here.

# Landing page brand: MILLENNIUM now matches the app

User: *"in landing page i want you to use the same font and same collor
combination for MILLENIUM"*.

The app's brand treatment is `.millennium-word` in `public/css/style.css`:
**Cinzel 900** (fallback `'Playfair Display', Didot, 'Bodoni MT', Georgia,
serif`) with a **metallic platinum/chrome gradient clipped to the text** —
greys `#737373 → #f2f2f2 → #737373` — plus a `drop-shadow`. The landing page's
`.brand-name` was plain `'Outfit', sans-serif` in a flat colour.

## Changes in `public/landing.html`
- Added `Cinzel:wght@700;800;900` to the Google Fonts link — the landing page
  is self-contained and did **not** load Cinzel, so without this the brand would
  have silently fallen back to Georgia.
- Rewrote `.brand-name` to mirror `.millennium-word` (same font stack, weight
  900, `letter-spacing: .05em`, same gradient stops, `background-clip: text`,
  `-webkit-text-fill-color: transparent`, same drop-shadow).
- Markup text `Millennium` → `MILLENNIUM` to match the app literally.

## The trap: the two files use OPPOSITE theme selectors
`style.css` is **dark-first**: `:root` is the dark palette and
`[data-theme="light"]` overrides it. So there, the *bright* chrome gradient is
the base rule and the *darker* one is the `[data-theme="light"]` override.

`landing.html` is **light-first**: its base `:root` is the light palette and
`[data-theme="dark"]` overrides it. So the gradients had to be inverted — the
darker chrome is the base rule and the bright chrome is behind
`[data-theme="dark"]`. Copying the two rules across verbatim would have given a
bright gradient on a white background (washed out) and a dark one on the dark
background (invisible). Worth remembering before porting any styled rule between
these two files.

## Verification
`tests/landing-page.test.cjs` extended 41 → **50** with a brand-parity section
that reads the **app's own `.millennium-word` from the sign-in portal** and
compares against the landing page: same font stack, same weight, Cinzel actually
loaded (`document.fonts.check`), gradient-clipped (not flat colour), and the
dark-theme gradient string **byte-identical** to the app's. Plus a light-theme
check that the darker chrome is used. Measured `.brand-name` = 120 px wide at
390 px (no overflow) and 127 px at 1440.

Full regression — **304 passed, 0 failed**: landing-page 50, no-refresh 32,
mobile-responsive 67, rental-privacy 51, ui-auth 16, session-expiry 9,
showcase-removal 40, profile-and-rental-form 39.
